# Repository Instructions

## Styling architecture

- Keep each built-in component's style definition in its owning `components/<Name>.styles.js` module. Use `customizeComponent(name, tasty(options))` or `customizeComponent(name, tasty(base, options))` for rendered roots. Shared bases own their defaults and must expose a registered customization name. Component markup imports its owner directly; do not restore the `GlobalStyles`, `LayoutComponents`, or `TastyComponents` aggregators.
- Initialize document foundations from the common page shell, independently of replaceable Header/Head components. Reserve `useGlobalStyles()` for document foundations and named generated-content bridges; register those rules during rendering, never on module import. MarkdownContent owns its generated-content bridges, and CodeGroup collects its code/syntax bridges when rendered independently.
- Use shared predefined states for appearance rules: `@light` and `@dark` for component styles, and `@system-light`/`@system-dark` inside document-root automatic appearance rules. Keep scheme media queries in `tasty-states.js`, not individual style trees.
- Tasty and Glaze configuration and style evaluation are build/server-only. Ship extracted static CSS, never Tasty/Glaze browser runtimes, serialized theme configuration, style registries, or hydration initialization. Keep `tastyIntegration({ islands: false })`. Use small client scripts for interactions on server-rendered markup; client islands must not import Cookbook styling, Tasty, or Glaze. Verify this boundary in real consumer builds, including custom themes/components.
- The rendered documentation site must ship only CSS generated by Tasty and Glaze. Do not add CSS files, Astro `<style>` blocks, inline `style` attributes, or CSS modules. Express component styles with `tasty()` and shared global rules with `useGlobalStyles()`.
- In new or modified style groups, model related descendant and pseudo-element rules as named Tasty sub-elements inside their owning `tasty()` or `useGlobalStyles()` style object (for example, `Label: { $: "> span", ... }`). Do not split component anatomy across additional `useGlobalStyles()` calls with composed selectors.
- Own renderer markup and behavior without importing vendor component styles.
- Every styled Cookbook component and every new or modified owned global/vendor bridge must support user customization through `theme.styles.<ComponentName>`. Accept only a partial Tasty style object from the user and merge it into the complete base style object inside the engine with `mergeStyles(baseStyles, configuredStyles)`. Use `customizeComponent()` for component roots and `resolveComponentStyles()` for global style trees. Register new names in `COOKBOOK_COMPONENT_NAMES`, publish every named Tasty sub-element in `COOKBOOK_COMPONENT_SUB_ELEMENTS`, and document the complete sub-element list for every configurable surface.
- Apply registered semantic typography roles with Tasty's `preset` property. Do not reproduce a preset by referencing its individual `$*-font-*` tokens or wire modifier internals such as `$bold-font-weight` by hand; use modifier syntax such as `preset: "strong"` or `preset: "h2 / strong"`.
- All component colors must use semantic theme color tokens. Expose every new color role through `theme.palette`, resolve it through Glaze for every supported scheme and contrast mode, and update the public types, schema, documentation, and tests. Do not hard-code presentational color values in components.
- Show the brand as a simple Glaze `from` declaration in theme configuration examples. Show other palette colors as relative or absolute Glaze declarations using `tone`, `base`, `contrast`, and saturation factors where needed. Literal color shorthand and structured brand hue/saturation/tone remain supported.
