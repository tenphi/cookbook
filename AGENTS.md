# Repository Instructions

## Styling architecture

- The rendered documentation site must ship only CSS generated by Tasty and Glaze. Do not add CSS files, Astro `<style>` blocks, inline `style` attributes, CSS modules, or Starlight component styles. Express component styles with `tasty()` and shared global rules with `useGlobalStyles()`.
- In new or modified style groups, model related descendant and pseudo-element rules as named Tasty sub-elements inside their owning `tasty()` or `useGlobalStyles()` style object (for example, `Label: { $: "> span", ... }`). Do not split component anatomy across additional `useGlobalStyles()` calls with composed selectors.
- When replacing a Starlight component, own the required markup and behavior without copying, importing, or retaining its styles.
- Every styled Cookbook component must expose its complete Tasty style object through `theme.styles.<ComponentName>` using `customizeComponent()`. Register new component names in `COOKBOOK_COMPONENT_NAMES` and document their supported anatomy keys.
- All component colors must use semantic theme color tokens. Expose every new color role through `theme.palette`, resolve it through Glaze for every supported scheme and contrast mode, and update the public types, schema, documentation, and tests. Do not hard-code presentational color values in components.
